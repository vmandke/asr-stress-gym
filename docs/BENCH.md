# Load generation and benchmark output — the frozen contract

This file exists so the load generator (M7) and the benchmarks that
consume it (M8) can be built in parallel without one waiting on the
other's source. **Everything below is a contract, not documentation of an
implementation.** If M7 needs to change one of these, it changes here
first.

Two things are frozen: `cmd/loadgen`'s command-line surface, and the CSV
it writes.

## The corpus

Everything that loads, benchmarks or fails over reads `corpus/large`,
generated by `scripts/gen_corpus_large.py`. It is **git-ignored** (~200MB)
and reproducible from `--seed`, so a fresh checkout must generate it once:

```bash
scripts/gen_corpus_large.py            # the default mix, ~200 clips
scripts/gen_corpus_large.py --count 40 # a faster subset, still every kind
```

The twelve committed clips in `corpus/` remain the ground truth for
protocol-level assertions. They are 1-30s and a single utterance apiece,
which makes them useless for measuring anything at scale.

Clips are laid out **one subdirectory per kind**, and each kind exists
because some behaviour is untestable without it:

| Kind | Length | Utterances | Speech ratio | What it is for |
|---|---|---|---|---|
| `monologue` | 10-20s | 1 | ~1.0 | the baseline |
| `dialogue` | 25-50s | 6-12, two voices | ~0.85 | several utterances per **session** — where per-utterance dedupe and revision-reset live, and where a session-wide bug hides behind a passing single-utterance test |
| `long_form` | 60-120s | 4-8 | ~0.95 | replay-cost bounding. At 15s the cap at the last committed final never binds; at two minutes it is the difference between recovering and not |
| `silence_heavy` | 30-60s | 3-6 | ~0.3 | the VAD economic argument at a realistic ratio, and pre-roll surviving a journal trim |
| `rapid_turns` | 20-40s | 10-20 | ~0.7 | utterance lifecycle churn: finals and resets arriving faster than a chunk boundary |
| `noisy` | 10-20s | 1 | ~1.0 | speech at 15dB SNR. A VAD tuned only against clean TTS is tuned against nothing |

`manifest.json` records every clip's **utterance boundaries** in
milliseconds, plus its measured `speech_ratio` and `utterances` count.
Those boundaries are what make it possible to assert that endpointing
fired in the right *places*, not merely that it fired — and the measured
speech ratio lets a benchmark correlate backend call volume against actual
speech content rather than against the `--speech-ratio` it asked for.

`cmd/loadgen` loads at most 64 distinct clips (a seeded sample), because
holding all ~200MB resident would make the generator larger than the
gateway it is measuring.

## `cmd/loadgen` — command-line surface

```
loadgen --streams N [options]
```

| Flag | Default | Meaning |
|---|---|---|
| `--streams N` | `1` | Concurrent sessions to hold open. |
| `--ramp DUR` | `0s` | Spread stream starts evenly over this window instead of opening all at once. `--streams 200 --ramp 20s` opens ten per second. |
| `--duration DUR` | `30s` | How long to keep generating after the ramp completes. |
| `--speech-ratio F` | `1.0` | Fraction of each stream's audio that is speech; the rest is digital silence. `1.0` streams the clip back to back, `0.5` alternates clip and equal-length silence. Drives the VAD economic argument. |
| `--jitter-ms N` | `0` | Uniform random delay, 0..N ms, added before each frame write. Models a real network. |
| `--drop-pct F` | `0` | Fraction of audio frames silently not sent, while still consuming their sequence number — the gateway must report `discontinuity`. |
| `--reconnect-every DUR` | `0` (never) | Each stream tears down its socket and reopens on this period, resuming from its last `ack`. |
| `--mode online\|offline` | `online` | Session mode declared in `session.start`. |
| `--corpus DIR` | `corpus/large` | Directory of WAV clips, searched recursively. Each stream picks one by seeded round-robin from a bounded sample (at most 64 distinct clips). |
| `--ws-url URL` | `$GATEWAY_WS_URL`, else `ws://localhost:7070/ws` | Gateway WebSocket endpoint. |
| `--out PATH` | *(none)* | Write the event CSV here. Omitted means summary only. |
| `--seed N` | `1` | Seeds clip choice, jitter and drops, so a run is reproducible. |

**Exit status is 0 whenever the run completed**, including runs in which
the gateway returned `overloaded` or streams saw errors — those are
*data*, not failures of the tool. A non-zero exit means loadgen itself
could not run (bad flags, unreadable corpus, gateway unreachable at
start). Assertions belong in `cmd/chaostest`, which is the thing that
decides pass or fail.

## Event CSV — `--out`

One header row, then one row per client-observed event. Written
incrementally, flushed at the end; a run killed mid-flight still leaves
valid rows.

```csv
ts_ms,stream_id,event,seq,latency_ms,streams_active,utterance_id,revision,failover_epoch
```

| Column | Type | Meaning |
|---|---|---|
| `ts_ms` | int | Milliseconds since the run started. Not a wall clock — a run is a self-contained timeline. |
| `stream_id` | int | 0-based stream index, stable across that stream's reconnects. |
| `event` | string | See the table below. |
| `seq` | int | The sequence number the event refers to, or `-1` when it refers to none. |
| `latency_ms` | float | Milliseconds, or empty when the event has no meaningful latency. Definition per event below. |
| `streams_active` | int | Streams with an open session at the moment this row was written. The x-axis of the latency-vs-concurrency chart. |
| `utterance_id` | string | From the event, or empty. |
| `revision` | int | From the event, or `-1`. |
| `failover_epoch` | int | From the event, or `-1`. |

### Event values and what `latency_ms` means for each

| `event` | Emitted when | `latency_ms` |
|---|---|---|
| `session_open` | `session.start` acked | Time from socket dial to ack. |
| `ack` | `ack` received | Time since the acked `seq` was written. |
| `partial` | `partial` received | Time since the frame that completed this partial's chunk was written — identified by the `seq` on the `ack` that immediately follows it. This is the **partial latency** milestone. See the note below. |
| `final` | `final` received | Time since `session.end` was written. This is the **final latency** milestone. |
| `partial.reset` | `partial.reset` received | Time since the most recent audio frame written — i.e. how long the failover stalled the stream. |
| `discontinuity` | `discontinuity` received | *(empty)* |
| `overloaded` | `overloaded` received | Time from dial to refusal. |
| `error` | `error` received, or transport failure | *(empty)* |
| `session_close` | Stream finished or gave up | Lifetime of the session. |

**A `partial` carries no sequence number**, so the obvious measurement —
time since the last frame written — is wrong in exactly the regime that
matters: when the gateway is slow, the partial for the chunk ending at
seq 9 arrives after frames 10..15 have gone out, and measuring against
frame 15 reports ~20ms for what was really ~120ms. Overload would look
fast. The protocol pins it down instead: the gateway emits `partial` then
`ack` for the same chunk, in that order, over one ordered socket, so the
next ack's `seq` identifies the frame that completed the chunk. loadgen
holds each partial until that ack arrives.

**These are client-observed latencies measured inside `docker compose`,
so they include a loopback hop the server-side milestones in
[DECISIONS.md](DECISIONS.md) exclude.** On the same host that term is
well under a millisecond and does not move a p95, but the two numbers are
not the same number and should not be presented as one. The locked
latency targets are server-side; these are what a client saw.

## Summary — stdout

Always printed, whether or not `--out` is set, as `key=value` lines so it
is greppable without being parsed:

```
streams_requested=200 streams_opened=198 streams_refused=2
audio_seconds_sent=1188.4 frames_sent=59420 frames_dropped=0
partial_p50_ms=41.2 partial_p95_ms=118.7
final_p50_ms=96.5 final_p95_ms=210.3
finals=198 duplicate_finals=0 discontinuities=0 errors=0 overloaded=2
```

`duplicate_finals` is counted client-side, independently of the gateway's
own `duplicate_finals_total`. Two independent observers of the invariant
that must stay zero are worth more than one.

`streams_refused` counts streams that never got a session at all;
`overloaded` counts refusal *events* wherever they occur. Only the first
is comparable against `--streams`, which is what a capacity run reads.

`finals` is **not** expected to equal `streams_opened`. Endpointing closes
an utterance at every detected pause, so one session over a `dialogue` or
`long_form` clip legitimately produces many finals.

## What M8 can rely on

- The flags and the CSV columns above, in that order, with that header.
- `--out` being safe to point at a path in a directory that already exists.
- Exit 0 on a completed run, so a benchmark script can read the CSV without
  special-casing.
- Backend-call volume for the `--speech-ratio` argument comes from the
  gateway's own metrics endpoint, not from this CSV — loadgen is a client
  and cannot see backend calls.
