# Corpus

Committed here at M1: ~20 short clips generated from known text, 16kHz
mono s16le, plus `transcripts.json` mapping each clip to its ground-truth
text. Known text means chaos and VAD assertions can check *correctness*
(does the first word survive pre-roll, does the transcript match), not
just latency — see [../docs/build-plan.md](../docs/build-plan.md#the-load-generator).

Not generated at container runtime and not downloaded on demand: a
reviewer on a bad connection still gets a working demo.

## Two corpora

| | `corpus/*.wav` | `corpus/large/*.wav` |
|---|---|---|
| Count | 12 | ~500 |
| Length | 1.2–30s | 10–20s |
| Committed? | **yes** | no — git-ignored, ~240MB |
| Generated by | `scripts/gen_corpus.sh` | `scripts/gen_corpus_large.py` |
| Used for | protocol-level assertions against a known transcript | everything that loads, benchmarks or fails over |

The committed clips are ground truth: small, stable and diffable, so a test
can name one and mean it forever. They are also **too short to measure
anything with** — 1–3s, one utterance each, so an utterance-length chart
built from them has no x-axis, replay-cost bounding is never stressed, and
endpointing never sees a pause.

`corpus/large` fixes that, and is a build artifact rather than an asset:
reproducible from `--seed`, so "the same corpus" is a number you pass
rather than 240MB you ship. Generate it once per checkout:

```bash
scripts/gen_corpus_large.py            # 500 clips, 10-20s, seed 1
scripts/gen_corpus_large.py --count 50 # a faster subset
```

macOS only, like `gen_corpus.sh` — it uses `say`, and runs on a developer
machine rather than in a Docker build or at container start.
